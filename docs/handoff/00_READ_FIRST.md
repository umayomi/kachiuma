# 00_READ_FIRST 【凍結・編集禁止】ファイル区分と更新権限

この handoff 一式は、後継モデル（Sonnet/Opus 等）が「不変の部分を誤って書き換えて
劣化させる」事故を防ぐため、**ファイル単位で編集権限を分離**している。

## ファイル区分（この表が唯一の権限定義）

| ファイル | 区分 | 後継モデルの権限 |
|---|---|---|
| SKILL.md | 凍結 | 編集禁止 |
| 00_READ_FIRST.md | 凍結 | 編集禁止 |
| 10_CORE_kachiuma.md | 凍結 | 編集禁止 |
| 20_METHODOLOGY_common.md | 凍結 | 編集禁止 |
| 30_PITFALLS.md | **追記専用** | 末尾に新項目の追加のみ可。既存項目の削除・書換・番号変更は禁止 |
| 40_STATE_kachiuma.md | **更新対象** | 更新可。ただし下記ルールに従う |
| BOOTSTRAP_general.md | 凍結 | 編集禁止（汎用読み込み書・他チャット用） |

## 40_STATE の更新ルール

1. 更新は**ユーザーの合意した決定**（スイープ採否・実測数値の更新・タスク完了等）を
   反映するときだけ行う。モデルの推測・見込みで書き換えない。
2. 冒頭の「更新履歴」に **日付・更新者モデル・変更点・根拠（何のログ/検証か）** を
   1行追記する。履歴のない更新は無効とみなす。
3. 数値を書くときは母数を添える（例: 28% (182件)）。母数のない率は書かない。
4. 凍結文書と矛盾する内容を書きたくなったら、それは STATE の更新ではなく
   「確定判断の変更」= ユーザーの明示判断が必要な案件。勝手に進めない。
   ユーザーが判断を覆した場合は、STATE の更新履歴にその旨を記録する
   （凍結文書は書き換えず、STATE 側が最新判断を持つ）。

## 30_PITFALLS の追記ルール

- 追記できるのは「実際に起きたインシデント」のみ。理論上の懸念は書かない。
- 形式: 通し番号を続け、分野・現象・対策・発生日を1項目にまとめる。

## 起動チェックリスト（毎セッション）

1. リポジトリ tarball を取得し、実状態を確認（記憶・コンテキストの古い状態を正としない。
   ユーザーが前回ファイルを貼り忘れている可能性を常に考慮）。
2. 40_STATE の更新履歴で「自分の知らない決定」が無いか確認。
3. 触る分野の 30_PITFALLS を読む。
4. 変更作業は 10_CORE の変更手順（既定OFFノブ・完全一致証明・スイープ3条件）に従う。
5. 成果物は /mnt/user-data/outputs へ全文で置き、present_files で提示、
   貼り替え順と確認ポイントを明記する。
6. セッションで大きな決定・数値・タスク状態が動いたら、40_STATE の更新版を
   成果物と一緒に出す（更新履歴つき）。
