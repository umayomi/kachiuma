# 30_PITFALLS 【追記専用】罠と対策（全て実インシデント由来）

既存項目の削除・書換・番号変更は禁止。追記は「実際に起きたインシデント」のみ、
末尾に通し番号で。理論上の懸念は書かない。

## A. GitHub Actions / yml

1. **run: ブロック内に `${{ }}` を書かない。** ブロック内 Python の中括弧（辞書・
   内包表記）まで式としてスキャンされ「Exceeded max expression」で Invalid workflow
   になる。**yaml.safe_load は通ってしまう**ため YAML 構文チェックでは検出不能。
   対策: 入力は `env:` で渡し `os.environ.get()` で受ける。配布前に全 run: ブロックへ
   `${{` が無いことを機械確認する。(2026-07 ability_proof.yml で発生)
2. yml の埋め込み Python は配布前に「抽出 → 10スペース剥がし → compile()」で検証する。
3. debug.yml の失敗ランは使い捨て診断の残骸。赤バツでも本番と無関係。追わない。
4. Actions の deps: jockey_db は BeautifulSoup 使用 → beautifulsoup4 / lxml を pip 行に。
   サンドボックスの pip は --break-system-packages 必須。

## B. Python / データ処理

5. **JSON 往復で int キーは str になる。** 馬番キーの dict を保存→読込すると
   `fin.get(umaban)` が全 None になり「全馬着順なし」に見える。読込直後に
   `{int(k): v ...}` で戻す。(2026-07 tally スタブ検証で発生)
6. self-test 内で `import 自モジュール as _m; _m.W_X=...` は `__main__` 実行中の
   関数に効かない（別実体）。`__main__` ではグローバルを直接書き換える。(2回発生)
7. **同名馬が実在する**（ジェニファーが2頭）。馬名だけでレース・馬を特定せず、
   同レースの他馬名・日付・horse_id で複合特定する。(2026-07 発生)
8. **netkeiba の成績表記「1-3-0-1」は 1着数-2着数-3着数-着外数。** 着順の列挙
   [1,2,2,2,9] と別物。ユーザーと突き合わせるときは相手の表記系に合わせる。(発生)
9. コピー時の `2>/dev/null` がファイル欠落を隠し、後段 ModuleNotFoundError の
   原因究明を遅らせた。配置コマンドでエラーを握りつぶさない。(発生)
10. 集計・合算は必ずコードで計算する。手計算の数字をレポートに書かない。

## C. サンドボックス環境の限界（誤検証の罠）

11. netkeiba / umarengod / Chrome に**到達不可**。ライブ取得コードは (a) スタブで
    ロジック検証、(b) 未確認の実レスポンス構造は「推定」と明記し診断出力を仕込む、
    (c) Actions かサイト実物で確認。複勝オッズ API(type=2) の配列並びはこの手順で
    実サイト確認済み（単勝 > 複勝上限 > 複勝下限 のサニティで判定できた）。
12. スタブ検証の空回り: 着順スタブをキャッシュ当日行から作ると当日行の無い馬は
    None → 「明細に入らない」がスタブ欠損か実バグか、1件追跡して確定させてから
    結論を書く。(発生)
13. Node スモークテストは /tmp に作るためセッションを跨いで残らない。ハーネス:
    document/localStorage/fetch をスタブ + `vm.runInThisContext`（require 不可）+
    日時依存は Date をクラス継承モック。壊れたらこの型で作り直す。

## D. カチウマ固有の設計ガード（10_CORE の確定判断を実装面から補強）

14. LAMBDA は 0.0 のまま。融合コードを「有効化すると良くなりそう」と思っても触らない。
15. HIDDEN_MAX_CLASS=4（OP・重賞バッジ非表示）を検証なしに外さない。
16. cp=None → 最下位評価を「中立0が自然」と直さない。それが元のバグ。
17. 新重みは既定OFF + 完全一致検証（型は 10_CORE §5）。検証無しの定数変更は禁止。
18. **1レースの結果で設計を変えない。** 直感 → 観測装置 → 母数 → スイープ → 3条件。
19. proof の窓は重複しうる。重なりを確認せず「独立に確認」と書かない。
20. 複数日を跨ぐ騎手処理は日付キー付きメモ（recompute.make_jk_tables_dated）。
    enrich.make_jk_tables は単日専用。(バグとして発見・recompute で回避済み)

## E. ユーザーとのやりとり

21. ファイルは全文貼り替えで渡す。diff・パッチ・行指定の編集指示は不可。
    複数ファイルは貼り替え順を明記。
22. リポジトリ実状態を毎回 tarball 取得で確認。前回ファイルの貼り忘れがありうる
    （サイト表示の文言から未反映を検知した実例あり）。
23. ユーザーの直感は仮説として全部検証に乗せる。正しかった例（ジェニファー型の
    取りこぼし）も、データが修正した例（場×距離最重要→距離が主役）もある。
24. 編集は anchor 方式（assert count==1 → replace）。広域置換で別箇所を壊さない。
25. 検証できなかったことは「検証できなかった」と書く。推定と実証を混ぜない。
